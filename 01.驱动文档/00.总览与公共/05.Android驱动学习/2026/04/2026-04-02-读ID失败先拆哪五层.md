## 读ID失败先拆哪五层

### 今日主题
很多驱动不是完全不进 `probe()`，而是 **进了以后卡在读 chip id / 版本寄存器 / 首包通信**。今天把这类问题拆成一条最实用的排查线：**资源 → 复位 → 总线 → 时序 → 上层现象**。

### 为什么今天学这个
这类问题最容易把人带偏：
- 日志表面像 “I2C 挂了”
- 实际可能是 `reset-gpio` 极性错了
- 也可能是 overlay 没把 regulator / pinctrl 喂对
- 甚至像 PN7221 那样，最后先炸的是 HAL / Framework，而不是最底层那一行 I/O

所以今天重点不是背命令，而是建立一个判断顺序：**读 ID 失败，先别急着改寄存器表，先确认设备有没有真的活过来。**

### 核心概念
#### 1. 读 ID 失败，通常不是“驱动主逻辑错”，而是前置条件没满足
驱动里第一次读 ID，本质是在问硬件一句话：**你醒了吗，而且我现在说话的方式对吗？**

如果这一步失败，优先怀疑 5 类问题：
1. **资源没到位**：regulator / clock / pinctrl / gpio 没生效
2. **复位没做对**：reset 脚极性、拉低拉高顺序、delay 不对
3. **总线没打通**：I2C 地址错、SPI mode / speed 不对、bus 没枚举
4. **时序不对**：上电后太早读、sleep out 后等待不够
5. **设备其实不是你以为的那版配置**：overlay 命中错、版本资源串了

#### 2. 先分“完全读不到”还是“偶发读错”
- **完全读不到**：更像资源、地址、复位、总线模式错误
- **偶发读错 / 压测后失败**：更像时序边界、恢复流程、并发 I/O 穿透

这个区分很重要。完全不通和偶发异常，不该走同一套修法。

#### 3. `read_id` 只是一个观察窗口
你库里的 GC9307 LCD 代码就很典型：`read_id` 前先 reset，再发特定命令读回芯片标识。这里真正关键的不是“命令表长什么样”，而是：
- reset 是否真的把屏复位了
- SPI 线序 / mode / speed 是否匹配
- 读 ID 前等待时间够不够

也就是说，**读 ID 失败常常只是前面某一步没站稳的结果。**

### 关键路径 / 关键文件
先盯这几类入口：
- DTS / overlay：`compatible`、`reg`、`*-supply`、`pinctrl-0`、`reset-gpio`、`interrupts`
- 驱动入口：`probe()`、`read_id` / `chip id` / `who_am_i` 附近
- 运行时确认：`/proc/device-tree/...`、`/sys/bus/i2c/devices`、`/sys/bus/spi/devices`
- defer 观察：`/sys/kernel/debug/devices_deferred`
- 日志主线：`dmesg` + 同时间窗 `logcat`

### 常用命令 / 日志点
```bash
dmesg | grep -i "probe\|fail\|defer\|gpio\|pinctrl\|regulator\|i2c\|spi"
cat /sys/kernel/debug/devices_deferred
ls /sys/bus/i2c/devices
ls /sys/bus/spi/devices
logcat -b all | grep -i "abort\|timeout\|nfc"
```
现场别一口气抓一堆；先回答这 4 个问题：
1. 节点是否真的生效
2. 驱动是否进过 `probe`
3. 资源申请是否成功
4. 第一条通信失败前，是否已有 reset / power / defer 异常

### 真实问题场景
#### 场景 1：GC9307 读屏 ID 不对
从你现有 LCD 代码看，GC9307 的 `read_id` 依赖 **先 reset，再发读 ID 命令**。所以如果 ID 不对，优先查：
- reset 脚有没有真的翻转
- SPI mode / speed 是否合适
- 屏上电后是否过早读寄存器
- 读到的是全 0 / 全 FF，还是固定错误值

经验上：**全 0 / 全 FF 更像链路根本没打通；固定错误值更像时序、模式或面板版本不匹配。**

#### 场景 2：PN7221 不是“读 ID”字面失败，但本质一样
你现有案例里，`CORE_RESET_NTF(0xA7)`、`write_unlocked failed`、`ret(-107)` 说明的不是 Java 层问题，而是 **芯片复位恢复后的首段通信不稳定**。这和普通 chip id 失败是同一类思路：
- 设备有没有先稳定上电
- recovery 窗口里有没有并发 I/O 穿透
- 是不是还没 ready 就开始发命令

#### 场景 3：SM6225 改了节点，现象却很怪
你现有 SM6225 文档已经把核心说透了：问题可能不在驱动，而在 **overlay 根本没命中到目标版本**。此时驱动代码看起来“像是资源都写了”，但真正运行时吃到的并不是你以为那套 regulator / pinctrl / gpio。

### 和当前项目的联系
这套方法能直接复用到你现在的库：
- **LCD**：先看 reset、SPI mode、上电后读 ID 时机
- **TP / Sensor**：先看 chip id 路径，不要一上来怀疑算法或上报逻辑
- **PN7221**：把 `0xA7` 和 `ret(-107)` 当成“恢复窗口通信失败”看
- **SM6225**：先验证 overlay 命中，再谈驱动里拿资源是否合理

一句话说，**读 ID 失败不是一个点的问题，而是一条链：配置有没有喂对、资源有没有起来、复位有没有做稳、总线有没有说通、时序有没有踩准。**

### 一句话总结
**看到 chip id / 首包通信失败，先查“设备有没有被正确唤醒并拿到对的资源”，再去改寄存器和初始化表。**
