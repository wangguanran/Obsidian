## PN7221不是只看I2C

### 今日主题
用你现有库里的 **PN7221** 做一张模块专题卡：为什么它表面是个 I2C 外设，但现场排查时，**不能只盯内核驱动和总线通信**，还必须把 **HAL、NCI stack、Framework** 一起看成一条链。

### 为什么今天学这个
很多普通外设出问题时，看到 `probe fail`、`read id fail`，思路还比较直接；但 NFC 尤其是 PN7221，不少现场会出现一种很迷惑的现象：
- 内核侧不像完全没起来
- I2C 也不是一直死透
- 最后炸出来的却是 `com.android.nfc` 或 `nfc_pn72xx@1.2-service` 的 `SIGABRT`

这时候如果还把它当“普通 I2C 设备驱动”看，就容易一直在底层兜圈子。

### 核心概念
#### 1. PN7221 的真正交付链，不止“驱动把芯片带起来”
把它先粗暴记成 4 层：
1. **板级与内核层**：电源、GPIO、IRQ、I2C、驱动初始化
2. **HAL 层**：`phNxpNciHal*` 负责和芯片按 NCI 协议说话
3. **Framework / NfcService**：管理开关、超时、恢复、上层能力
4. **App/业务表现**：能不能打开 NFC、能不能读卡、压测会不会崩

所以对 PN7221 来说，**芯片能应答 ≠ NFC 功能真正稳定可用**。

#### 2. `CORE_RESET_NTF` 是理解异常链的关键观察点
你现有文档已经把这件事讲得很透：异常窗口里如果看到 `CORE_RESET_NTF`，后面就要立刻追它的 `reason`。

特别是 `0xA7`，你库里的案例已经明确：
- 含义不是“Java 层抽风”
- 而是芯片在 POR 后的接口层，收到了不符合预期的包序列
- 后续会把问题一路传成 timeout、recovery，最后演化到 abort

也就是说，**`0xA7` 不是结果展示，而是链路中间那个最值钱的证据点。**

#### 3. HAL abort 和 Framework abort 不是一回事
这是 PN7221 很容易误判的地方。

你库里的资料已经区分了两条路径：
- **HAL service abort**：更靠近底层恢复失败、I2C 连续失败、`write_unlocked failed`、`ret(-107)` 这条线
- **Framework abort**：更靠近 `NFA_DM_NFCC_TIMEOUT_EVT`、watchdog、上层恢复策略这条线

现场如果只说一句“NFC 崩了”，信息量太低。更有用的问法是：
**到底是谁先 abort，abort 前最后一个关键证据是什么？**

### 常用命令 / 日志点
不用撒网式乱抓，先盯同一时间窗里的 4 组关键词：

```bash
logcat -b all | grep -i "nfc\|abort\|timeout\|watchdog"
dmesg | grep -i "nfc\|i2c\|irq\|reset"
logcat -b all | grep -i "CORE_RESET_NTF\|NFA_DM_NFCC_TIMEOUT_EVT"
logcat -b all | grep -i "write_unlocked failed\|ret(-107)"
```

现场先回答 4 个问题：
1. 先出现的是 `CORE_RESET_NTF` 还是 I2C 连续失败？
2. reason 是不是 `0xA7` 或其他异常码？
3. 先崩的是 HAL service 还是 `com.android.nfc`？
4. 崩溃前是否正好处在 enable/disable、recovery、压测切换窗口？

### 真实问题场景
你现有案例里，压测时每 3 秒开关 NFC 并验证读卡，最终出现这条典型链：
- `CORE_RESET_NTF(0xA7)`
- `NFA_DM_NFCC_TIMEOUT_EVT`
- `com.android.nfc` `SIGABRT`
- 恢复阶段又出现 `write_unlocked failed`、`ret(-107)`
- 最后 `nfc_pn72xx@1.2-service` 也 `SIGABRT`

这条链最值得记住的不是“哪一行代码 abort 了”，而是：
**开关电/复位窗口里的并发读写穿透，可能先把芯片喂进错误包序，再把恢复流程拖进更深的通信失败。**

所以修法重点通常不是“把 abort 注释掉”，而是：
- 收紧 power off / closing 窗口
- 阻断 disable 过程中的新 I/O
- 串行化开关与读写
- 让 POR 后第一批包序满足芯片预期

### 和当前项目的联系
这张卡对你现在的知识库很贴：
- 它和前面讲过的“读 ID 失败五层拆解”是同一思路，只是 PN7221 多了 HAL/Framework 两层
- 它和 `SM6225 overlay` 那张卡也能连起来：底层资源喂错，会在更上层表现成奇怪的 timeout 或 abort
- 它还能反过来提醒你：以后看 NFC 日志，别只盯 kernel，也别只盯 app，要按 **内核 → HAL → NCI → Framework** 的顺序串证据

一句现场话可以直接记住：
**PN7221 出问题时，I2C 只是入口，真正要排的是一整条恢复链。**

### 一句话总结
**PN7221 不是“会不会通 I2C”这么简单；判断它稳不稳定，要把 `CORE_RESET_NTF`、HAL recovery、NCI timeout、Framework abort 当成一条完整链来看。**
