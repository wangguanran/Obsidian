# 2026-W15 本周驱动学习回顾

本周主题比较集中，核心都围绕 **PN7221/NFC 异常链路分析** 和 **abort/timeout 现场调试方法**。重点不是再把 NFC 当成“一个 I2C 外设问题”去看，而是开始把 **内核、HAL、NCI stack、Framework** 当成一条完整链路来排障。

## 本周最重要的 4 个知识点

### 1. PN7221 现场排查，不能只盯 I2C
本周最关键的认知升级，是把 PN7221 从“总线通不通”提升到“整条交付链稳不稳”来理解。

实际排查时，至少要同时看四层：
- 板级与内核层：电源、GPIO、IRQ、I2C、驱动初始化
- HAL 层：`phNxpNciHal*`
- NCI stack / Framework 层：timeout、watchdog、恢复逻辑
- 业务表现层：开关 NFC、读卡、压测稳定性

也就是说，**芯片能应答，不等于 NFC 功能真的稳定可用**。

---

### 2. `CORE_RESET_NTF`，尤其 `reason=0xA7`，是高价值证据点
这周几张卡都在反复指向同一个核心观察点：
**`0xA7` 比最终的 abort 更接近根因。**

它不是“Java 层抽风”，而更像是：
- 芯片 POR 后
- 接口层收到不符合预期的包序列
- 随后触发 timeout、恢复失败，最后才演化成 abort

这意味着以后看日志时，不能只盯 `SIGABRT`，而要反过来追：
**在 abort 之前，有没有 `CORE_RESET_NTF(0xA7)` 这样的中间异常证据。**

---

### 3. 双 abort 不是两个根因，通常是一条异常链的双向扩散
本周把 `com.android.nfc` 和 `nfc_pn72xx@1.2-service` 同窗崩溃这类现象拆得比较清楚了。

更合理的理解是：
- **Framework 链**：`CORE_RESET_NTF(0xA7)` → `NFA_DM_NFCC_TIMEOUT_EVT` → `com.android.nfc` abort
- **HAL 链**：恢复/关闭阶段继续恶化 → `write_unlocked failed` / `ret(-107)` → `nfc_pn72xx@1.2-service` abort

所以以后遇到“双 abort”时，第一反应不该是“系统随机坏了”，而应该是：
**先判谁是先发链，谁是扩散链。**

---

### 4. 调试方法上，先切时间窗，再判层级
这周的方法论也比较清晰了：
看到 `abort`、`timeout`、`service died`，不要一把梭翻全量日志。

更有效的做法是：
1. 先找爆点时间戳
2. 向前回看 5~10 秒
3. 向后看 2~3 秒确认扩散结果
4. 再分层判断 kernel / HAL / Framework 谁先异常

一句话记住就是：
**谁先异常，看时间；根因在哪，看层级。**

## 这周已经串起来的概念

本周最明显的进步，是把下面几件事串成了同一条链：

- **POR 后包序异常** 会先体现在 `CORE_RESET_NTF(0xA7)`
- 这个异常会继续放大成 **NCI timeout**
- 上层先感知时，可能表现为 **Framework abort**
- 恢复/关闭阶段如果通信继续恶化，又会拖出 **HAL abort**
- 所以最终看到的“双 abort”，很多时候只是同一根因在不同层的收尾表现

这说明已经不再是“看到哪层报错就修哪层”的思路，而开始具备 **按链路串证据、按时序判根因** 的排障框架了。

## 还需要补课的点

### 1. `0xA7` 对应的底层包序异常，还需要再落到更具体的交互时序
现在已经知道它指向 POR 后接口层收到异常包序，但还不够细。
下阶段值得继续补：
- POR 后第一批命令/响应的标准顺序
- 哪些 enable/disable/recovery 并发窗口最容易打乱包序
- 典型错误时序在 log 上会长什么样

### 2. HAL recovery 与 Framework watchdog 的边界，还可以再拆细
现在已经能粗分两条链，但对：
- 哪些场景 HAL 会主动 fail-fast
- 哪些场景 Framework 是被动超时后 abort
- 两边在 recovery 窗口里的衔接关系
还可以再做一张更偏源码视角的对照卡。

### 3. 调试方法还需要进一步模板化
这周已经形成“按时间窗切片”的意识，但还可以继续沉淀成更稳定的现场模板：
- 先抓哪些关键词
- 先问哪几个问题
- 什么现象优先怀疑底层，什么现象优先怀疑恢复流程

## 下周最值得优先学什么

### 优先级 1：POR 后早期通信时序与异常包序
这是当前最接近根因的一块，继续深挖最划算。
重点建议：
- 把 `CORE_RESET_NTF(0xA7)` 前后的标准/异常时序整理成一张链路卡
- 明确“错误包序”到底可能发生在 enable、disable、recovery 哪个窗口

### 优先级 2：NFC recovery/close 窗口里的并发约束
本周已经多次指向这个方向：
**真正要修的通常不是 abort 本身，而是避免异常走到 abort。**
所以下周值得重点学：
- 如何阻断 disable 过程中的新 I/O
- 如何串行化 `disable / recovery / read-write`
- 如何收紧 `power off / closing` 窗口

### 优先级 3：沉淀一张 NFC 现场速查卡
如果能把这周的内容收敛成一张现场卡，以后排查效率会明显提高。
建议内容包括：
- 必抓日志
- 必看关键词
- 必问 5 个问题
- Framework 链和 HAL 链的快速判定法
