## PN7221双abort先判哪条线

### 今日主题
同一个异常窗口里，`com.android.nfc` 和 `nfc_pn72xx@1.2-service` 都可能 `SIGABRT`。今天只学一件事：**双 abort 不要并案，先判哪条是先发链，哪条是扩散链。**

### 为什么今天学这个
现场最容易犯的错，是看到两个进程都崩，就把结论写成“系统不稳定”“NFC随机崩溃”。
但你现有 PN7221 资料已经说明：这类现场通常不是“两处独立坏了”，而是**一个底层触发物，沿着两条恢复链往上扩散**。

### 核心概念
#### 1. 先找触发物，不要先盯崩溃点
在你现有案例里，真正值钱的不是 `abort` 本身，而是它前面的：
- `CORE_RESET_NTF`
- `reason=0xA7`
- `NFA_DM_NFCC_TIMEOUT_EVT`
- `write_unlocked failed`
- `i2c ret(-107)`

口诀：**先看 reset reason，再看 timeout，再看谁 abort。**

#### 2. Framework abort 和 HAL abort 是两条链
可以先粗分成：
- **Framework 链**：`CORE_RESET_NTF(0xA7)` → NCI stack 判异常 → `NFA_DM_NFCC_TIMEOUT_EVT` → `com.android.nfc` abort
- **HAL 链**：恢复/关闭阶段通信继续恶化 → `write_unlocked failed` / `ret(-107)` → `nfc_pn72xx@1.2-service` abort

所以“两个都崩”不代表有两个根因，更常见的是：**同一窗口里先失控，再分别触发两边的 fail-fast。**

#### 3. `0xA7` 比最终崩溃更接近根因
你库里的归档已经给出定义：`0xA7` 表示 POR 后接口层收到了不符合期望的包序列。
翻成人话就是：**芯片刚复位回来，第一批通信次序就乱了。**
后面的 timeout、abort，更像这次乱序的后果。

### 常用命令 / 日志点
```bash
logcat -b all | grep -i "CORE_RESET_NTF\|NFA_DM_NFCC_TIMEOUT_EVT\|abort"
logcat -b all | grep -i "write_unlocked failed\|ret(-107)"
dmesg | grep -i "nfc\|i2c\|irq\|reset"
```
抓日志时别贪多，优先保住**同一时间窗前后 5~10 秒**。

### 真实问题场景
用你现在的 PN7221 压测案例，建议按这个顺序读：
1. 先出现 `CORE_RESET_NTF(0xA7)`
2. 随后进入 `NFA_DM_NFCC_TIMEOUT_EVT`
3. `com.android.nfc` 先走到 abort
4. 恢复阶段继续出现 `write_unlocked failed`、`ret(-107)`
5. `nfc_pn72xx@1.2-service` 再 abort

这个顺序说明两件事：
- `com.android.nfc` 的 abort 不是起点，只是上层先感知到恢复失败
- HAL service 后续再 abort，说明下层通信在 recovery/close 窗口里继续恶化

### 和当前项目的联系
这和你当前项目的价值不在“知道哪行 abort”，而在于能指导改法：
- 先收紧 `power off/closing` 窗口，阻断新 I/O
- 再串行化 `disable / recovery / read-write`
- 重点避免 POR 后早期错误包继续打进 NFCC

也就是说，**修复目标不是消灭 abort 日志，而是让异常不要走到 abort 那一步。**

### 一句话总结
**PN7221 双 abort 现场，先看 `0xA7` 和 timeout 谁先出现，再分清 Framework 链与 HAL 链，别把两个结果误当成两个根因。**
