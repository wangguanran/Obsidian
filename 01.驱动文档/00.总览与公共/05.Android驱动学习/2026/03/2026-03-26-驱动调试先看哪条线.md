## 驱动调试先看哪条线

### 今日主题
不是“哪里报错就盯哪里”，而是先把 **日志层级、链路位置、失败阶段** 分开看。

### 为什么今天学这个
Android 驱动现场最容易浪费时间的事，就是一上来改代码。
其实很多问题第一步根本不是“修”，而是先判定：
- 是 **没 match / 没 probe**，还是 **probe 进了但初始化失败**
- 是 **内核侧资源问题**，还是 **HAL / Framework 被下游异常带崩**
- 是 **节点没生效**，还是 **版本 overlay 选错了**

### 核心概念
#### 1. 先分 3 层日志
- **kernel**：`dmesg` / `kmsg`，看 probe、gpio、irq、regulator、i2c/spi 错误
- **HAL/service**：看 open、close、read/write、超时、重试、abort
- **framework/app**：看功能表现、服务重启、超时兜底

口诀：**上层在叫，不代表根因在上层。**

#### 2. 先问“卡在哪一阶段”
排查顺序最好固定成：
1. **设备有没有出现**：总线下是否有实例 / 运行时 DT 是否存在节点
2. **驱动有没有绑定**：有没有 match 上、probe 是否执行
3. **资源有没有拿到**：gpio / pinctrl / regulator / clk / irq 是否成功
4. **通信是否正常**：读 ID、收中断、I2C/SPI 收发是否成功
5. **上层是否被连带打崩**：HAL timeout、service abort、framework watchdog

#### 3. “不工作”至少分 4 类
- **完全不进 probe**：优先看 DTS、compatible、bus、镜像是否编入
- **probe 进了但 defer**：优先看 `devices_deferred` 和依赖资源
- **probe 成功但功能异常**：优先看时序、寄存器初始化、irq、中断风暴
- **上层报错/崩溃**：往下追 kernel/HAL 时间线，不要只盯 Java log

### 关键路径 / 关键文件
- 设备树与 overlay：`arch/arm64/boot/dts`、厂商 `qcom/.../devicetree/...`
- 驱动入口：`of_match_table`、`id_table`、`probe()`、`remove()`
- 运行时确认：`/proc/device-tree/...`
- defer 观察：`/sys/kernel/debug/devices_deferred`
- 总线与绑定：`/sys/bus/i2c/devices`、`/sys/bus/platform/devices`、`/sys/bus/*/drivers`

### 常用命令 / 日志点
```bash
dmesg | grep -i "probe\|defer\|fail\|gpio\|irq\|regulator\|i2c"
logcat -b all | grep -i "nfc\|hal\|abort\|timeout"
cat /sys/kernel/debug/devices_deferred
ls /sys/bus/i2c/devices && ls /sys/bus/i2c/drivers
cat /proc/device-tree/.../compatible
```
别贪多，先抓到 **第一条异常日志**，再往前后扩 5~10 秒时间窗。

### 真实问题场景
#### 场景 1：SM6225 改了节点但现象没变
先别怀疑驱动逻辑，先查：
- 改的是不是最终生效那份 `dtbo`
- `board-id / stage` 是否命中目标 overlay
- 资源是不是来自错误版本 overlay

你现有 SM6225 笔记已经说明了重点：**节点存在 ≠ 当前版本真的吃到了这套资源。**

#### 场景 2：PN7221 看起来是上层崩溃
现有案例里，`com.android.nfc` 和 `nfc_pn72xx@1.2-service` 的 `SIGABRT`，并不等于根因在 app。
更可靠的看法是沿时间线倒着追：
- 先看到 `CORE_RESET_NTF` reason
- 再看是否出现 `NFA_DM_NFCC_TIMEOUT_EVT`
- 同窗确认有没有 `i2c ret(-107)`、`write_unlocked failed`

这说明：**Framework/HAL 的 abort 可能只是下游通信异常的结果。**

### 和当前项目的联系
今天这套方法，能直接复用到你现在的库：
- **SM6225**：先判定 overlay 命中，再看 regulator/pinctrl/gpio 绑定
- **PN7221**：先拼完整时间线，再区分 HAL 主动 abort、framework timeout、I2C 根因
- **TP / Sensor / Charger**：统一先分“没进 probe”还是“进 probe 后失败”，别一上来就改初始化代码

### 一句话总结
**驱动调试的第一步不是改代码，而是先判断问题卡在：匹配、资源、通信，还是上层连带报错。阶段一分清，排查效率会高很多。**
