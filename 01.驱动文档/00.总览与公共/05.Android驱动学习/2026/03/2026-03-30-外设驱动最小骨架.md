## 外设驱动最小骨架

### 今日主题
把一份 Android 外设驱动，压成一条最值得记住的主线：**注册驱动 → 匹配设备 → probe 拿资源 → 注册功能接口 → 上层可用**。

### 为什么今天学这个
上周已经把 `match / DTS / 调试 / 案例 / 速查` 分开讲过了。
这周周一不再重复概念，而是把它们捏成一张“最小骨架图”。

因为你后面无论看的是：
- TP
- Sensor
- Charger
- NFC
- Camera

表面差很多，真正落到代码里，第一轮都在回答同一件事：
**这份驱动到底靠什么把硬件带起来，并把能力交给系统。**

### 核心概念
#### 1. 一份驱动，至少有 5 个骨架动作
先记这条主线：
1. **驱动注册**：`platform_driver_register()` / `i2c_add_driver()` / `spi_register_driver()`
2. **设备匹配**：`of_match_table`、`id_table` 和 dts 里的 `compatible` 对上
3. **probe 初始化**：拿 gpio / irq / regulator / clk / pinctrl，确认通信正常
4. **注册对外能力**：把能力挂进 input、power_supply、misc、v4l2 等子系统
5. **运行期维护**：中断处理、读写、error recovery、suspend/resume、remove

很多人只盯 `probe()`，但其实 `probe` 只是中段，不是整部戏。

#### 2. `probe()` 真正干的不是“写业务”，而是“搭运行环境”
一个靠谱的 `probe()` 往往先做这些：
- 校验 dts 资源是否齐
- 申请供电、时钟、GPIO、中断
- 做 reset / 上电 / 基础通信
- 读取 chip id 或版本信息
- 初始化寄存器默认值
- 注册到对应内核子系统

所以 `probe` 失败，常见根因通常不是算法错，而是：
**资源没喂对、时序没踩对、总线没打通。**

#### 3. 真正决定“上层能不能看到功能”的，是最后一步注册
驱动把芯片带起来，还不算结束。
还得看它最终向谁报到：
- TP / 传感器：常挂 `input` 或 sensor 框架
- Charger / Gauge：常挂 `power_supply`
- NFC：既有内核侧设备，也有 HAL / service 往上接
- Camera：通常接 v4l2、media controller、sensor framework

也就是说：
**芯片活了 ≠ 功能对外可见；必须完成“向系统注册能力”这一步。**

### 关键路径 / 关键文件
拿到一个新驱动文件，建议固定先找这 6 个点：
1. `of_match_table`
2. `id_table`
3. `probe()`
4. 中断线程或 workqueue
5. 子系统注册入口（如 `input_register_device`、`power_supply_register`）
6. `suspend/resume` 或 error recovery

源码外再配合看两类文件：
- **DTS / DTSI / DTBO**：设备怎么接、资源怎么喂
- **模块知识页 / FAQ / 案例页**：项目里这个器件曾踩过什么坑

### 常用命令 / 日志点
先别贪多，盯住最小闭环：
```bash
dmesg | grep -i "probe\|fail\|defer\|gpio\|irq\|regulator\|i2c"
cat /sys/kernel/debug/devices_deferred
ls /sys/bus/i2c/devices && ls /sys/bus/i2c/drivers
cat /proc/device-tree/.../compatible
```

排查顺序建议固定成：
1. 有没有设备节点
2. 有没有驱动绑定
3. probe 有没有进
4. 资源有没有申请成功
5. 功能有没有注册到目标子系统

### 真实问题场景
#### 场景：代码在、节点也在，但功能就是没有
这种时候别直接冲进寄存器表。
先问 3 句：
- 是 **没 match**，还是 **进 probe 后失败**？
- 是 **资源没拿到**，还是 **已经带起但没完成子系统注册**？
- 是 **内核底层没起来**，还是 **HAL / framework 还没接住**？

这 3 句能把很多“感觉都不对”的现场，快速压缩成明确阶段。

### 和当前项目的联系
这张骨架卡，和你现在库里的东西是能直接对上的：
- **PN7221**：不只要看 I2C 节点和 `probe`，还要看异常恢复、HAL/service 链路有没有把能力继续往上交付。
- **SM6225 overlay 分流**：说明“设备匹配前的资源路由”就可能决定后面整条骨架是否成立；版本没命中，后面全白搭。
- **TP / Sensor**：很多 bringup 卡点都在 `reset/irq/pinctrl/chip id` 这段，也就是 probe 的资源与通信阶段。
- **Charger（SC8885S、SGM41513 等）**：芯片就算能通，如果 `power_supply` 注册不完整，上层看到的充电状态也会异常。
- **Camera**：往往不是单个 `probe` 就结束，而是还要挂进更复杂的媒体框架，所以“功能注册”这一步更重要。

你可以把它粗暴记成一句现场话：
**先别问驱动写了多少，先问这 5 步闭环有没有走完。**

### 一句话总结
**一份 Android 外设驱动的最小骨架，不是只有 `probe()`，而是“注册、匹配、拿资源、注册能力、运行维护”五步闭环；少一步，功能都可能看起来像没起来。**
