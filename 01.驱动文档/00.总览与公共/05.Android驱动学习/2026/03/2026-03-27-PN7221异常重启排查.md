## PN7221异常重启怎么顺藤摸瓜

### 今日主题
用你现有 PN7221 案例，走一遍 **“现象 → 时间线 → 调用链 → 根因判断”** 的真实排查。

### 为什么今天学这个
周四讲的是“先分阶段”。今天不讲抽象方法，直接落到你库里最像现场的一个问题：
- 压测时 `com.android.nfc` 会 `SIGABRT`
- `nfc_pn72xx@1.2-service` 也会 `SIGABRT`
- 看起来像上层随机崩，其实不是

这类问题很适合练手，因为它会逼你养成一个关键习惯：**不要被最后一个崩溃进程带跑，要沿时间线往前找第一颗雷。**

### 核心概念
#### 1. `abort` 只是结果，不是起点
你现有笔记已经确认：
- Framework 侧有自己的 abort 链路
- HAL 侧也存在显式 `abort()`

所以看到 `SIGABRT`，第一反应不该是“这里崩了”，而要问：
**是谁主动触发的？它前面收到了什么异常信号？**

#### 2. 这次关键触发物不是 Java 异常，而是 `CORE_RESET_NTF`
现有案例里，异常窗口前会看到 `CORE_RESET_NTF`，其中 reason=`0xA7`。
结合你库里的归档，这个码的语义不是“普通复位完成”，而是 **POR 后接口层收到了不符合期望的包序列**。

这句话翻成人话就是：
**芯片刚复位回来，本该先走一套规矩的初始化包，结果总线上先闯进了不该来的东西。**

#### 3. 同一个现场，可能同时存在两条崩溃链
别把它们混成一条：
- **Framework 链**：`CORE_RESET_NTF(0xA7)` → NCI stack 认定异常 → `NFA_DM_NFCC_TIMEOUT_EVT` → `com.android.nfc` abort
- **HAL service 链**：恢复/关闭阶段持续 I2C 失败，出现 `write_unlocked failed`、`ret(-107)`，重试耗尽后 service abort

所以正确结论不是“App 崩了”，而是：
**下层通信异常先把恢复流程打乱，随后上层和 HAL 各自走到了自己的 fail-fast 终点。**

### 常用命令 / 日志点
先抓“同一时间窗”里的联合证据，别拆着看：
```bash
dmesg | grep -i "pn7221\|i2c\|nfc"
logcat -b all | grep -i "CORE_RESET_NTF\|NFA_DM_NFCC_TIMEOUT_EVT\|abort\|write_unlocked\|ret(-107)"
```

现场最值钱的不是日志多，而是这 4 个点有没有串起来：
1. `CORE_RESET_NTF` 的 reason 是不是 `0xA7`
2. 后面有没有 `NFA_DM_NFCC_TIMEOUT_EVT`
3. 同窗是否出现 `write_unlocked failed` / `i2c ret(-107)`
4. 最后崩的是 Framework、HAL，还是两边都崩

### 真实问题场景
#### 场景：每 3 秒开关 NFC 并验卡，压测中途服务重启
按你现有归档，这类问题更像下面这条主线：
1. 高频开关让 **关断/上电/读写** 三件事发生了时间重叠
2. NFCC 在 POR 后收到异常包序，报出 `CORE_RESET_NTF(0xA7)`
3. NCI stack 把它判为异常 reset，进入 timeout / recovery
4. 恢复阶段 I2C 又不稳定，继续出现 `ret(-107)`
5. 最后 Framework 和 HAL 分别走到 abort

这里最容易误判的点是：
- 误判成“Android app 自己崩”
- 误判成“HAL 单点 bug”
- 误判成“只要屏蔽 abort 就好了”

其实都偏了。**abort 更像保险丝，真正要修的是开关窗口与 I/O 并发穿透。**

### 和当前项目的联系
这不是泛泛案例，和你现有项目材料是直接对得上的：
- 平台是 `[项目代号]_A14/LA.VENDOR.13.2.1.R2`
- 你已经把 HAL 显式 abort 路径、Framework watchdog 路径、`0xA7` 定义都整理进库了
- 当前最有价值的工程动作，不是先改大逻辑，而是先**收紧 power off/closing 窗口，阻断新 I/O**
- 第二步是把 **disable、recovery、read/write** 串行化，避免 POR 后早期错误包继续冲进芯片

换句话说，这个案例教你的不是“NFC 有多特殊”，而是一个很通用的现场思路：
**看到上层崩溃，先去抓底层异常触发物；看到恢复失败，再查恢复窗口里有没有并发穿透。**

### 一句话总结
**PN7221 这类 abort 问题，真正的排查起点不是谁崩了，而是 `CORE_RESET_NTF(0xA7)` 为什么出现，以及它出现前后的 I/O、复位、关断时序有没有打架。**
