## 驱动为什么能挂上去

### 今日主题
Linux device model、driver match、probe。

### 为什么今天学这个
很多 Android 驱动问题，表面现象都很像：
- 节点明明写了，但驱动没起来
- 代码明明在，probe 却不进
- 外设明明焊上去了，系统却像没看见一样

这类问题的根本，绕不开三个词：**device、match、probe**。

今天先把这根骨头搭好，后面你再去看 TP、Sensor、Charger、NFC、Camera 这些模块时，脑子里就不会只剩下“驱动坏了”这种很虚的判断，而是会先问：
**设备有没有被枚举出来？驱动有没有 match 上？probe 到底有没有跑？**

### 核心概念
#### 1. 设备和驱动是分开的
在 Linux 里，设备（device）和驱动（driver）不是一回事。

可以把它理解成：
- **设备**：系统里“有这么个硬件或节点”
- **驱动**：系统里“有这么段代码说我会处理这类硬件”

只有当两边**匹配成功**，内核才会调用驱动的 `probe()`。

所以驱动不是“代码放进内核就一定执行”，而是：
> 总线先发现设备，驱动再声明自己支持什么设备，内核把两边拿来 match，match 成功后才进入 probe。

#### 2. match 成功，probe 才会执行
`probe()` 可以理解成驱动真正开始干活的入口。

通常在 `probe()` 里会做这些事：
- 申请 GPIO / IRQ
- 获取 regulator / clock
- 读芯片 ID
- 初始化寄存器
- 注册 input / misc / netdev 等设备

所以：
- **probe 不进** → 先查匹配链路
- **probe 进了但失败** → 再查初始化细节

这两个分层一定要分清，不然很容易一上来就钻错方向。

#### 3. 常见总线只是匹配入口不同，但主线一样
虽然 platform、I2C、SPI 看起来不一样，但主线其实一致：

- **platform device**
  - 很多板级设备、SoC 设备走这个
  - 常见依赖：`of_match_table` + device tree 的 `compatible`

- **I2C device**
  - TP、Sensor、部分 Charger/NFC 常见
  - 匹配可能走：
    - `of_match_table`
    - `i2c_device_id`

- **SPI device**
  - 逻辑类似 I2C
  - 常见还是 `of_match_table` + `compatible`

你可以先记住一句简单的话：
> **不同总线只是“怎么找到设备”的入口不同，但最终都得走到 match → probe 这条主线。**

#### 4. `compatible` 是 Android 设备侧最常见的第一入口
在 Android BSP 里，很多外设问题最后都会回到 device tree。

因为常见流程是：
- dts 里写一个节点
- 节点里放 `compatible = "xxx,yyy"`
- 驱动里 `of_match_table` 也写支持的 compatible
- 两边对上了，才有机会进入 probe

所以很多“驱动没起”的第一枪，不是查 C 代码逻辑，而是：
- DTS 节点有没有
- `compatible` 对不对
- 节点挂的总线对不对

#### 5. `-EPROBE_DEFER` 是非常常见的“看起来像没起，其实是依赖没齐”
有一种很坑的情况：
- 驱动不是完全没 match 上
- 它是 match 上了，也进了 `probe()`
- 但因为 regulator / GPIO / clock / pinctrl 之类依赖没准备好，返回了 `-EPROBE_DEFER`

这时表面上看起来像“驱动没起来”，但本质已经不是 match 问题，而是**依赖时机问题**。

这个点在 Charger、Sensor、TP 里都很常见。

### 关键路径 / 关键文件
如果你想追这条链路，最值得先看的地方是这些：

#### Linux 通用主干
- `drivers/base/`
- `drivers/base/platform.c`
- `include/linux/device.h`
- `include/linux/platform_device.h`
- `include/linux/of_device.h`
- `include/linux/mod_devicetable.h`

#### I2C / SPI 相关
- `drivers/i2c/`
- `include/linux/i2c.h`
- `drivers/spi/`
- `include/linux/spi/spi.h`

#### 驱动里最关键的 3 个点
拿到一个驱动文件时，先找：
1. `of_match_table`
2. `id_table`
3. `probe()`

如果这三个点你都能快速定位，后面排查就顺很多。

#### DTS 常见位置
不同平台位置会不一样，但常见会在：
- `arch/arm64/boot/dts/...`
- 或厂商私有 kernel tree 下的 `qcom/`、`sprd/`、`vendor/` 等目录

### 常用命令 / 日志点
下面这几个命令，真的非常高频：

#### 1. 先看驱动日志
```bash
dmesg | grep -i <driver_name>
dmesg | grep -i "probe\|defer\|fail"
```

#### 2. 查设备有没有出现在总线上
```bash
ls /sys/bus/i2c/devices
ls /sys/bus/platform/devices
ls /sys/bus/spi/devices
```

#### 3. 查驱动有没有注册
```bash
ls /sys/bus/i2c/drivers
ls /sys/bus/platform/drivers
```

#### 4. 查 DTS 里的 compatible
```bash
grep -R "compatible" arch/arm64/boot/dts -n | grep <chip_or_vendor>
```

#### 5. 查运行时 device tree
```bash
cat /proc/device-tree/.../compatible
```

#### 6. 如果系统支持，查 deferred probe
```bash
cat /sys/kernel/debug/devices_deferred
```

这个文件特别有用，因为它能告诉你：
**不是没 probe，而是 probe 被延后了。**

### 真实问题场景
#### 场景 1：TP 节点写了，但 probe 完全不进
这时先不要急着看手势、坐标、上报。

优先检查：
1. DTS 节点是不是挂在正确的 I2C 控制器下
2. `compatible` 是否和驱动里的 `of_match_table` 一致
3. 驱动本身是否编进了当前镜像
4. 总线号是否对得上

如果这些都没问题，再看 GPIO / IRQ / reset。

#### 场景 2：Sensor 有日志，但一直初始化失败
这时和“probe 不进”是两码事。

如果日志已经打到了：
- 读 chip id
- init reg
- request irq

那说明它其实已经 match 成功并进入 probe 了。此时重点就不是“为什么没挂上”，而是：
- 上电顺序对不对
- 芯片 ID 是否读错
- pinctrl / regulator 有没有准备好
- IRQ 是否有效

这就是为什么分清“没进 probe”和“进了 probe 但失败”很重要。

#### 场景 3：NFC / Charger 上层报错，但根因在底层匹配链路
很多 Android 设备问题看起来是在 HAL 或 framework 层：
- 打不开
- 初始化失败
- 服务异常

但如果底层设备都没正确绑定上，HAL 再往上也只能报错。

所以遇到这类问题时，不要直接把视角锁死在上层，先回到底层问一句：
> 设备是不是根本就没有成功 match / probe？

### 和当前项目的联系
今天这篇虽然是基础骨架，但和你现在的知识库其实贴得很紧：

- **TP**：像 `CST916E`、`BL7163` 这种，第一层就是总线、compatible、IRQ、reset
- **Sensor**：像 `QMA6100P`、`DA265`、`IAM20680`，先分清楚是“没 match 上”还是“probe 里初始化失败”
- **NFC**：`PN7221` 表面问题可能出现在 HAL，但底层设备是否起来，仍然要回到底层匹配链路
- **Charger**：很多充电 IC 的 bringup，表面像功能异常，底层先看节点、总线、依赖资源是否齐

也就是说，今天学的不是抽象理论，而是后面几乎所有模块专题的**共同入口**。

### 一句话总结
**驱动能不能工作，第一步不是看“代码写得多不多”，而是先确认：设备有没有被枚举出来、驱动有没有 match 上、probe 到底有没有跑。**
