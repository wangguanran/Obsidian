# 2026-W18 本周驱动学习回顾

本周依然没有新增 Android 驱动学习日卡，所以这次回顾的重点不是扩写新知识，而是判断当前学习主线有没有跑偏、哪些关键认知已经足够稳定、下周该把力气重新压到哪里。结合最近几张卡片，这周的主题仍然集中在 **PN7221 / NFC 异常链路分析**，尤其是 **不要被结果日志带偏，要沿时间线往前追根因** 这条方法线。

## 本周最重要的 4 个知识点

### 1. 连续两周没有新增卡片，本身就是需要正视的问题
这已经不是单次漏记，而是学习闭环出现了停摆。对驱动学习来说，最危险的不是暂时不会某个点，而是“方法刚建立起来，记录就断了”，这样很容易把前面好不容易形成的排障框架又磨散。

所以本周最先要记住的，不是某个新术语，而是：
- 当前学习系统的主线是对的
- 但节奏已经明显失稳
- 下周要先恢复稳定输出，再谈扩展主题

### 2. `abort`、`service died`、读写失败，更像扩散结果，不一定是起点
前面几张卡片已经反复说明：看到 NFC 或驱动异常时，不能抓住最终报错就一路猛追。很多日志只是故障扩散到后段后的表现，真正高价值的证据通常出现在更早的时间窗。

这条认识现在已经可以当默认原则：
- 先找第一次异常
- 再看后续扩散
- 不要把最后一条红字当根因

### 3. PN7221 问题必须按整条链路看，不能只盯 I2C
最近主线里最稳的一点，是已经接受了“不是只看 I2C”这个事实。即使表面现象落在总线读写、abort 或 HAL 行为上，也要同时看：
- 上电 / POR 后早期时序
- NCI 交互是否正常推进
- HAL recovery / disable / close 是否互相打架
- Framework 侧是不是在放大底层问题

也就是说，排障视角已经从“单点查错”升级成“分层看扩散路径”。

### 4. 现在最值得深挖的，不是更广的知识面，而是更窄的关键窗口
前面的学习已经把范围压缩到了少数几个高价值窗口：
- `CORE_RESET_NTF(0xA7)` 前后到底发生了什么
- POR 后标准握手和异常握手差在哪
- recovery / disable / close 的并发边界怎么判

这说明下一步不该继续横向开新坑，而是把这几个窗口拆得更细，细到能直接指导日志定位和代码阅读。

## 哪些概念已经串起来了

当前已经比较牢的主线有：
- **结果日志不等于根因**
- **日志要按时间线向前追，不要只盯故障爆点**
- **NFC 驱动异常需要跨 kernel / HAL / NCI / Framework 分层判断**
- **双 abort、timeout、service died 往往是同一早期异常在不同层面的传播**

这些概念已经不再是零碎提示，而是在慢慢形成一套可复用的驱动排障方法。

## 还需要补课的地方

- 连续两周没有新卡，说明“每日沉淀”机制要优先修复，否则知识链会继续断
- `0xA7` 所在的早期时序还缺一张真正的对照卡，最好把正常包序和异常包序并排写清楚
- recovery / close 这类状态收口阶段，还缺一张更偏状态机或源码视角的方法卡

## 下周最值得优先学什么

### 优先级 1：恢复每日学习卡片输出
先把节奏救回来，这是所有后续积累的前提。

### 优先级 2：补“POR 后标准时序 vs 异常时序”对照卡
重点把 `CORE_RESET_NTF(0xA7)` 放进完整交互过程里，而不是只把它当异常关键词记忆。

### 优先级 3：补“recovery / disable / close 并发边界”方法卡
目标是把哪些阶段可以并发、哪些阶段必须收口，整理成排障时能直接套用的判断框架。
