# 2026-W13-本周驱动学习回顾

这一周没有铺很散，主线其实很清楚：先把 Android 驱动排查最底层的骨架搭起来，再把设备树、调试方法、真实案例和速查入口串成一条能落地的排查线。

本周实际覆盖了 5 个核心主题：
- [[2026-03-23-驱动为什么能挂上去]]：先搞清楚 device / match / probe 这条主线
- [[2026-03-24-设备树怎么把驱动喂起来]]：理解 DTS / pinctrl / gpio / irq / overlay 为什么直接决定驱动能不能活
- [[2026-03-26-驱动调试先看哪条线]]：把问题拆成匹配、资源、通信、上层这几个阶段
- [[2026-03-27-PN7221异常重启排查]]：用真实案例练“现象 → 时间线 → 根因”的排查方式
- [[2026-03-28-总线与日志速查卡]]：把现场最常用的检查口收敛成一页速查

如果用一句话概括，这周不是在背知识点，而是在建立一个以后反复能用的判断框架：
**驱动问题先看链路卡在哪，而不是一上来就改代码。**

## 最重要的知识点
- **驱动能不能起来，第一关永远是 match → probe。**
  不是代码进了内核就会跑，必须先有 device、再能匹配 driver、最后才会进入 `probe()`。以后看到“驱动没起”，脑子里第一反应应该是：设备有没有枚举、驱动有没有 match、probe 到底进没进。

- **DTS 是资源合同，不是附属配置。**
  `compatible` 只是开始；总线位置、`reg`、pinctrl、gpio、irq、regulator、clock、版本 overlay，都会直接决定驱动有没有饭吃。节点“写了”不等于配置“生效了”。

- **`probe` 不进、`probe` 失败、`probe defer` 必须强行分层。**
  这三类问题表面都像“驱动没起来”，但根因完全不同：
  - 不进 probe：优先查 DTS、总线、compatible、镜像是否编入
  - 进 probe 但失败：优先查资源、上电、时序、chip id、irq
  - defer：优先查 regulator / gpio / clock / pinctrl 等依赖资源是否到位

- **上层 abort 往往只是结果，不是起点。**
  PN7221 这一例特别典型：`com.android.nfc` 和 HAL service 的 `SIGABRT` 只是最后表现，真正有价值的证据是更早出现的 `CORE_RESET_NTF(0xA7)`、I2C 异常、恢复路径失败。

- **现场排查要靠“时间线 + 固定入口”，不要靠感觉跳。**
  `dmesg`、`/sys/bus/*`、`/proc/device-tree`、`devices_deferred`、HAL/framework 日志，这些入口一旦固定下来，很多问题都能先缩小到“没枚举 / 没绑定 / 缺资源 / 通信失败”四类之一。

## 哪些概念已经串起来了
- **从设备树到驱动入口的链已经通了。**
  现在可以把“DTS 节点 → compatible → 总线匹配 → probe → 资源申请 → 初始化”当成一条连续链路来看，而不是把 DTS 和 `.c` 文件割裂开。

- **从内核到上层的故障传导路径也开始成形了。**
  不再只是看到 app/HAL 崩溃就停在那，而是会顺着时间线往前追：底层通信异常怎么一路传到 HAL，再把 framework 带崩。

- **方法论和案例已经连上了。**
  这周不是纯理论：前面的 match / DTS / 调试分层，后面都在 PN7221 案例里得到了对应验证，所以这套方法已经不只是“知道”，而是开始具备“可拿去用”的感觉。

- **速查卡把抽象知识压成了现场动作。**
  后续无论是 TP、Sensor、NFC 还是 Charger，第一轮检查基本都可以复用这套入口，而不是每次都从零开始想。

## 还需要补课的地方
- **单模块 bringup 还不够细。**
  这周更多是在搭公共骨架，真正落到 TP / Sensor / Charger 各自的初始化路径、chip id 读取、input/reporting、irq 处理，还需要继续拆。

- **overlay / 运行时 DT 的验证还要更熟。**
  已经知道“源码改了不等于最终生效”，但要进一步练成现场习惯：先确认最终 dtbo 是否命中，再谈驱动问题。

- **资源时序类问题还需要更多案例。**
  比如 reset 极性、pinctrl 工作态、regulator 上电时序、I2C 速率这类点，现在知道重要，但还缺几个能反复对照的真实样本。

- **本周“模块专题入口”这一环略显空。**
  原计划里周三想从 TP / Sensor 模块切一个轻量专题，但这周实际还没单独展开，所以下周最好尽快补上，不然容易一直停留在公共方法层。

## 下周优先主题
- **优先把一个具体模块完整拆一遍。**
  建议先从 TP 或加速度计 Sensor 入手，按“节点 → match → probe → 资源 → chip id → 中断 / 数据上报”走完整链路。这样能把本周的骨架真正落到具体模块上。

- **把 overlay 生效验证做成固定动作。**
  以后碰到“改了没效果”的问题，默认先查运行时 DT、最终 dtbo 和版本命中逻辑，不要直接怀疑驱动主逻辑。

- **继续补“资源 / 时序 / 中断”这条线。**
  因为很多驱动并不是没匹配上，而是资源没拿对、脚态不对、时序没满足，这会是从“知道怎么查”走向“能更快查准”的关键一步。

## 一句话给下周的自己
别急着钻代码细节，先把链路和阶段钉死；阶段一分清，很多看起来乱成一团的问题其实会自己变简单。
