## 设备树怎么把驱动喂起来

### 今日主题
Device Tree、pinctrl、gpio、irq，以及为什么“节点写了”不等于“驱动就能正常工作”。

### 为什么今天学这个
昨天那张卡片讲的是：**device 要先 match，驱动才会 probe**。

那今天就接着补最关键的一层：
很多 Android 驱动并不是“C 代码写好了就行”，而是还得有人把它需要的资源喂进去。这个“喂资源”的地方，很多时候就是 **DTS / DTSI / DTBO**。

所以现场最常见的坑不是代码语法错，而是下面这些更像工程问题的东西：
- 节点挂错总线
- `compatible` 写得能看但对不上
- GPIO 名字对了，极性错了
- IRQ 配了，但 pinctrl 没把脚切到正确状态
- regulator 在 base dtsi 和 overlay 里重复或冲突
- 版本差异本来该放 overlay，结果硬塞进公共 dtsi

你现在知识库里已经有很典型的真实材料：
- **SM6225 的 board-id / stage / overlay 分流说明**
- **PN7221 的 I2C 节点补丁**
- **ST77916 的面板 dtsi 配置**

它们刚好能说明：
> 设备树不是“写个 compatible 就完了”，而是把总线位置、供电、GPIO、时序、版本差异一起描述清楚，驱动才真的有饭吃。

### 核心概念
#### 1. 设备树本质上是在描述“这个硬件怎么接的”
驱动代码只是在说：
- 我支持哪些芯片
- 我拿到资源后怎么初始化

而 DTS 说的是另一件事：
- 这个芯片挂在哪条总线上
- I2C 地址是多少 / SPI CS 是谁
- 中断脚是哪根
- reset/enable/ven 脚是哪根
- 供电来自哪个 regulator
- 上电时序、显示参数、版本差异是什么

所以别把 DTS 理解成“附属配置”。
它其实是**硬件连接关系的文字版原理图**。

#### 2. 一个节点至少要回答 4 个问题
拿一个外设节点来看，通常至少要回答这 4 件事：

1. **你是谁**
   - `compatible`
2. **你在哪**
   - 挂在哪个 bus 下、`reg` 是多少
3. **你靠什么活着**
   - `vdd-supply`、`vio-supply`、clock、pinctrl
4. **你怎么和系统交互**
   - `irq-gpio`、`reset-gpio`、`enable-gpio`、`interrupts`

少任何一块，都可能出现一种很烦的现象：
**驱动不是完全没写，而是“看起来像没这个器件”。**

#### 3. pinctrl 不是点缀，它经常决定硬件脚到底有没有真的工作
很多人一开始只盯 GPIO 编号，但忽略 pinctrl。

GPIO 号写对，不代表管脚状态就对。
你还得看：
- 这根脚有没有 mux 成 gpio / i2c / irq 对应功能
- 上拉下拉对不对
- drive strength 对不对
- 默认态是不是输出高/低

这也是为什么有些问题特别迷：
- 节点在
- 驱动也进 probe
- 但读 ID 失败 / 中断不来 / 上电无反应

根因可能根本不是驱动主逻辑，而是 **pinctrl 没把脚状态配对**。

#### 4. overlay 的职责不是“补丁味 include”，而是版本差异隔离
你知识库里的 `sm6225_dts_boardid_stage分流说明.md` 非常值得反复看。
它讲得很清楚：
- bootloader 先根据 `board-id` / `stage` 选中目标 overlay
- **base dtsi 保留公共层**
- **v101 / v102 overlay 承载版本差异节点**
- 驱动只消费分流后的标准资源，不要自己再做版本 if-else

这个思路很工程化，而且很对。
因为一旦版本差异留在公共 dtsi 里，最容易出现三种事故：
- A 版本改动把 B 版本带崩
- 节点“看着有”，但其实被后续 overlay 覆盖了
- 驱动里也写版本判断，DTS 里也写版本判断，最后双重分流，谁都说不清

### 关键路径 / 关键文件
#### 1. 设备树主路径
常见位置通常在：
- `arch/arm64/boot/dts/...`
- Qualcomm 平台常见在：`kernel_platform/qcom/proprietary/devicetree/qcom/...`
- Unisoc / MTK 也会有各自平台目录

#### 2. 版本分流关键点
结合你现有 SM6225 笔记，重点不是只看 `.dts`，而是一起看：
- bootloader 里的 DT 匹配逻辑
- Makefile 里到底构建了哪些 `.dtbo`
- base `.dtsi`
- 版本 overlay：如 `v101` / `v102`

一句话：
**你改了节点，不代表这个节点会被最终加载；先确认那份 dtbo 真被选中了。**

#### 3. 真实例子一：PN7221 的 I2C 节点长什么样
你库里 PN7221 参考补丁里，节点挂在 `&i2c11` 下：
- `compatible = "nxp,nxpnfc"`
- `reg = <0x28>`
- `nxp,nxpnfc-irq`
- `nxp,nxpnfc-ven`
- `nxp,nxpnfc-mode_sw`
- `pinctrl-names = "default"`
- `pinctrl-0 = <&io_supply_activate>`
- 还把 `clock-frequency` 调到了 `<1000000>`

这段配置非常适合拿来当“节点不是只写 compatible”的样板。

因为它同时把几个关键事实都交代了：
- 芯片在 **I2C11** 上，不是在别的控制器上
- 地址是 `0x28`
- IRQ / VEN / mode_sw 都有明确脚位
- pinctrl 要让相关脚进入可工作的状态
- 总线速率也可能是 bringup 成败的一部分

如果你把它误挂到 `i2c14`，而补丁里 `i2c14` 又被 `status = "disabled"`，那驱动代码再漂亮也白搭。

#### 4. 真实例子二：ST77916 的 dtsi 说明“配置”不只有 GPIO
`lcd_st77916_boe_mipi.dtsi` 这个文件也很有代表性。
它里面不是只有一个简单节点，而是直接描述了：
- `work-mode`
- `lane-number`
- `fps`
- `power-on-sequence`
- `power-off-sequence`
- 一大段 `init-data`
- `display-timings`

这类模块提醒我们：
**有些驱动问题不是“节点没写全”，而是“时序参数和初始化表没喂对”。**

也就是说，设备树 / 配置的职责有两层：
- 一层是“让驱动找到设备”
- 一层是“让驱动按正确参数把设备带起来”

LCD、Camera、部分 Sensor 在这点上特别明显。

#### 5. 真实例子三：SM6225 overlay 分流说明资源绑定比节点存在更重要
在那份 SM6225 笔记里，重点不是“有没有节点”，而是：
- `regulator-fixed`
- `pinctrl-0`
- `gpio-pwm`
- `se5v` 这样的供电和功能节点到底来自哪个 overlay

这说明一个很现场的事实：
**同名节点存在，并不代表资源来源正确。**
如果资源来自错误的 overlay，表面上像“节点都在”，实际上驱动吃到的是另一套硬件版本的配置。

### 常用命令 / 日志点
#### 1. 先查源码侧 DTS 定义
```bash
grep -R "nxpnfc\|st77916\|compatible" -n arch/arm64/boot/dts kernel_platform/qcom/proprietary/devicetree/qcom
```

#### 2. 查节点最后有没有进运行时设备树
```bash
cat /proc/device-tree/.../compatible
cat /proc/device-tree/.../status
```

如果源码里有、运行时没有，优先怀疑：
- 改的不是最终生效那份 dts/dtbo
- overlay 没编进去
- bootloader 没选中目标 dtbo

#### 3. 查 deferred probe
```bash
cat /sys/kernel/debug/devices_deferred
```

这一步很重要。
因为很多时候不是节点错得离谱，而是 regulator / gpio / clock 依赖没齐，导致一直 defer。

#### 4. 看日志里有没有资源申请失败
```bash
dmesg | grep -i "gpio\|pinctrl\|regulator\|irq\|probe\|defer"
```

#### 5. 查总线和设备实例
```bash
ls /sys/bus/i2c/devices
ls /sys/bus/platform/devices
```

### 真实问题场景
#### 场景 1：节点写了，probe 还是不进
第一反应别直接改驱动。
先按这个顺序查：
1. 节点是不是挂在正确 bus 下
2. `status` 是不是 `okay`
3. `compatible` 是否和驱动 `of_match_table` 对上
4. 最终运行时 DT 里有没有这个节点
5. 当前机型到底加载了哪个 dtbo

很多“没进 probe”根因都在前四步里，尤其是第 4、5 步。

#### 场景 2：probe 进了，但读 ID 失败
这时重点转成资源问题：
- reset 脚极性是否正确
- irq 脚是否真的是中断功能态
- supply 是否真的拉起
- pinctrl 默认态有没有把脚配对
- 时序是否满足芯片要求

这类问题在 TP、Sensor、NFC 特别高频。

#### 场景 3：不同硬件版本互相串扰
这类就优先按 SM6225 那套思路看：
- 公共层和差异层有没有分离
- 版本差异是不是还残留在 base dtsi
- overlay 是否精确命中而不是 best-fit 回落

如果版本路由做得不干净，调试会非常痛苦：
你以为自己在修一个模块，实际上是在修“错误版本的资源绑定”。

### 和当前项目的联系
今天这个主题和你现有知识库连接得非常紧，不是泛讲：

- **PN7221**：已经有真实的 I2C 节点、GPIO、pinctrl、时钟频率样例，特别适合作为“外设节点最小闭环”模板。
- **SM6225**：已经有完整的 board-id / stage / overlay 分流案例，能直接用来建立“版本差异要前置在 DT 匹配层”的工程意识。
- **ST77916**：现成 dtsi 就能说明，某些模块除了 match 之外，更依赖参数表、时序、显示 timing 这类配置质量。
- **TP / Sensor / Charger**：虽然你当前笔记有的还在总览阶段，但排查套路其实已经能先统一：**先看节点位置，再看资源绑定，再看时序参数，最后才是驱动细节。**

所以今天学的不是“怎么背 DTS 语法”，而是建立一个更实用的判断：
> 当驱动不起、功能异常、跨版本表现不一致时，先把设备树当成“硬件接线和资源合同”来查，而不是只盯着 `.c` 文件。

### 一句话总结
**设备树不是把芯片名字登记上去，而是把“这颗芯片接在哪、靠什么供电、哪些脚控制它、哪个版本生效”一次性交代清楚；交代不清，驱动就算 match 上了，也很可能还是起不来。**
